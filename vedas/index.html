FAILURE_MODES.TXT 01 / THE FAILURE [ □ ]
01

THE FAILURE

Ephemeral contexts erase architectural truth.

§ 1.0

A fresh context window provides speed and focus. It is also where institutional knowledge vanishes. When an AI session ends, its rationale disappears unless the repository enforces strict epistemic persistence.

01

The unrecorded invariant

Session two reintroduces a naive pattern because session one only discussed the restriction in chat. The code compiles, but the system architecture degrades.

02

The epistemic hallucination

A handoff claims a subsystem works because the author assumes it does. Nobody ran the test command. The next session builds atop unverified speculation.

03

The sycophantic opener rut

Without hard lexical and behavioral firewalls, models lapse into predictable, repetitive pleasantries and stock empathy clichés, diluting focus and token budgets.

The problem is not that AI models hallucinate. It is that standard repositories permit unverified claims to pose as ground truth.

EPISTEMICS.TXT 02 / THREE SPEEDS OF TRUTH [ □ ]
02

THE FOUNDATION

Three speeds of truth: Śruti, Smṛti, and Vartamāna.

§ 2.0

In traditional software development, documentation is treated as a uniform pile of text. Vedas separates repository truth into three distinct temporal tiers, each governed by strict mutability rules.

IMMUTABLE / ETERNAL

Śruti: System Axioms

The bedrock laws of physics for the project. These invariants cannot be violated, relaxed, or edited without explicit maintainer consent.

  • docs/INVARIANTS.md houses core rules (INV-001 to INV-008).
  • Every invariant is bidirectional and citeable.
  • Mechanically guarded by automated lint tools.

APPEND-ONLY / EPOCHAL

Smṛti: Architecture & History

Institutional memory and historical precedent. Past decisions are superseded rather than erased, showing why dead ends were rejected.

  • docs/DECISIONS.md stores architectural decisions.
  • ROADMAP.md assigns stable, permanent task identifiers.
  • docs/CHANGELOG.md captures user-facing evolution.

REWRITE / LIVING PRESENT

Vartamāna: Living State

The immediate present moment. Stale claims are deleted immediately. The file is capped at 80 lines and overwritten every session.

  • docs/HANDOFF.md records verified current status.
  • Every bullet must carry a Pramāṇa proof badge.
  • Old entries are condensed into Sūtras or purged.
VEDANGAS.TXT 03 / REPOSITORY TOPOLOGY [ □ ]
03

REPOSITORY ANATOMY

The Six Vedāṅgas: Ancient sciences of structure.

§ 3.0

Just as classical scholars maintained oral texts without textual decay for millennia through six specialized disciplines, Vedas organizes repository architecture across six auxiliary limbs.

ŚIKṢĀ: PHONETICS & ORTHOGRAPHY

The Lexical Firewall (INV-006)

Enforces strict stylistic hygiene across all documentation and comments. Bans generic stock empathy, chat filler, and typographical quirks like em dashes to maintain crisp, machine-verifiable prose.

CHANDAS: METRICAL BOUNDS

Token & Line Economy (INV-005)

Imposes strict structural bounds. Session handoffs are strictly capped at 80 lines, and core architectural propositions (Sūtras) must not exceed 25 words. Brevity preserves cognitive bandwidth.

VYĀKARAṆA: FORMAL GRAMMAR

Contract & Schema Linters

Mechanically guarantees repository integrity through tools/check_vedas.py. Validates invariant reciprocity, verifies cross-references, and blocks malformed handoffs before commit.

NIRUKTA: ETYMOLOGY & LEXICON

Canonical Glossary & Terminology

Maintains unambiguous domain vocabulary in docs/GLOSSARY.md. Defines canonical terms, their historical counterparts, and nearby traps to avoid semantic drift between sessions.

JYOTIṢA: CHRONOMETRY & CALENDAR

Immutable Task IDs (INV-003)

Tracks roadmap execution with immutable identifiers (e.g. P1-01, P2-04). Tasks are never renumbered or repurposed. Abandoned tasks record what was learned.

KALPA: RITUAL PROCEDURE

The 5-Stage Session Ritual

The standard operating procedure executed on every session entry and exit. Governs orientation, verification, surgical changes, validation, and handoff compilation.

EPISTEMIC VERIFICATION

Pramāṇa proof tags & the Nyāya sequence.

§ 4.0

In Vedas, vague assertions like "the exporter works" are prohibited. Every claim must carry a Pramāṇa badge indicating its exact source of epistemic authority.

The Five Pramāṇa Epistemic Badges

[OBSERVED] Direct verification. Confirmed by executing a test or tool in the current session.
[DEDUCED] Logical deduction. Inferred from static analysis, type proofs, or invariants.
[CONTRACT] Formal invariant or schema contract defined in Śruti or architecture docs.
[HYPOTHESIS] Working theory or unverified speculation. Requires subsequent test verification.
[UNTESTED] Existing capability not executed in this environment or session.

Nyāya Pañca-Avayava: The 5-Step Proof Sequence

When resolving defects or adding features, agents follow the classical Nyāya five-part syllogism to guarantee reproducible changes:

01 Pratijñā (Proposition) State the required behavior or bug clearly. Example: "Opener ruts occur when the last three assistant responses share identical starting tokens."
02 Hetu (Defect Reason) State the causal root mechanism producing the failure. Example: "Context generation lacks a negative penalty for preceding opening n-grams."
03 Udāharaṇa (Negative Proof) Author a localized, offline test proving the defect exists. Observe the test fail cleanly before writing implementation code (INV-007).
04 Upanaya (Implementation) Apply the minimal, surgical code modification required to satisfy the failing test condition.
05 Nigamana (Verification) Re-run the entire test suite to verify that the failure is resolved and no regressions were introduced. Mark with [OBSERVED].

QUICK REFERENCE

The Epistemic Cheat Sheet.

§ 6.0

A fast, interactive desktop reference for daily use during agent sessions. Click the tabs below to copy exact patterns and commands.

Session Entry Ritual (Start of Session)

1. Read docs/HANDOFF.md
2. Read docs/INVARIANTS.md (Śruti core rules)
3. Run python3 tools/check_vedas.py --template
4. Run fast regression tests (docs/TESTING.md)
5. Inspect git status to verify clean working tree

Session Exit Ritual (Handoff & Exit)

1. Run offline verification tests
2. Run python3 tools/check_vedas.py --template
3. Update docs/HANDOFF.md (<80 lines, with Pramāṇa badges)
4. Check git diff for unrelated changes or em dashes
5. Commit and push clean state

How to Tag Claims in docs/HANDOFF.md

Every claim regarding test results, subsystem health, or environmental support must begin with one of these tags:

[OBSERVED] Test suite passes: 119/119 tests clean in 0.42s.
[CONTRACT] Invariant INV-006 strictly rejects all em dashes.
[DEDUCED] Parser handles UTF-8 correctly because tokenizer accepts bytes.
[HYPOTHESIS] Flaky test on Safari caused by missing SpeechSynthesis mock.
[UNTESTED] Audio playback on mobile WebKit not yet validated.

The Nyāya Pañca-Avayava Checklist

Use this five-step sequence for every bug fix or feature implementation:

Pratijñā (Proposition): The bug to fix or feature to add
Hetu (Defect Reason): The causal mechanical reason for the issue
Udāharaṇa (Negative Proof): Write failing offline regression test first
Upanaya (Implementation): Apply surgical, minimal code fix
Nigamana (Verification): Verify test passes cleanly [OBSERVED]

Sūtra Authoring Rules

Sūtras compress complex architectural laws into dense, memorable propositions:

  • Brevity: Under 25 words per Sūtra.
  • Clarity: Zero ambiguous adjectives, zero fluff.
  • Completeness: Unconditionally true within its domain.
  • Consolidation: When a handoff exceeds 80 lines, background learnings are consolidated into immutable Sūtras inside docs/INVARIANTS.md.
Example: "INV-006: Siksa requires zero em dashes across all documentation and comments."

Vedas Śruti Invariants Matrix (INV-001 to INV-008)

INV-001: Every project fact has exactly one authoritative home.
INV-002: Decisions record the discarded path, not just the winner.
INV-003: Roadmap task IDs are permanent and immutable.
INV-004: All truth claims must carry an explicit Pramāṇa badge.
INV-005: HANDOFF.md must never exceed 80 lines.
INV-006: Lexical Firewall enforces zero em dashes in prose or code.
INV-007: Every bugfix requires a prior negative test proof.
INV-008: Subconscious consolidation compresses learnings into Sūtras.

LINEAGE & ADOPTION

Evolving from The Manifold.

§ 8.0

Vedas is a direct fork of The Manifold. While The Manifold established the principle of separating repository memory into speeds of truth, Vedas enriches that foundation with classical Vedic epistemology, formal Pramāṇa badges, and the 5-step Nyāya proof sequence.

Adopting Vedas in an Existing Repository

To initialize Vedas in your project, copy the template files into your repository root:

cp -r vedas/docs . && cp vedas/tools/check_vedas.py tools/ && cp vedas/AGENTS.md .
python3 tools/check_vedas.py
